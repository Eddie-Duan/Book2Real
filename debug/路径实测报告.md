### ⚠️ 关键发现：DeepSeek 模型名有 4 种写法，只有 1 种是后端在用的（且它是错的）

实测 4 个候选模型名（真实调用）：

| 模型名 | 结果 |
|---|---|
| `deepseek-chat` | ✅ 有效，返回正文（`cloud.py` / `.env` 在用） |
| `deepseek-flash` | ✅ 有效（= 官方「V4.1 Flash」的真实模型名） |
| `deepseek-v4-pro` | ✅ 有效（= 官方「V4 Pro」） |
| `deepseek-v4.1-flash` | ❌ **400：`The supported API model names are deepseek-flash, deepseek-v4-pro`** |

**后端默认用的正是 `deepseek-v4.1-flash`**（`backend/app/config.py:124` 的 fallback），而 `.env` 里 `LLM_MODEL=` 留空，于是后端每次 `/api/ask` 都：
```
ERROR app.pipeline.turn: LLM failed, using extractive fallback
RuntimeError: llm 400: ... but you passed deepseek-v4.1-flash
```
→ 永远降级到抽取式规则问答，DeepSeek LLM 形同虚设。

**验证修复**：启动时设 `LLM_MODEL=deepseek-chat`，再 `/api/ask` → 无 400、LLM 正常作答。
**建议**：`.env` 加 `LLM_MODEL=deepseek-chat`（一行即可），或改 `config.py:124` 默认值为 `deepseek-chat`；并同步 `docs/API_KEYS.md` 与项目说明书里的模型名口径。

> 附带观察：LLM 模式下 `/api/ask` 的 `evidence` 为 0 条（生成式无引用），抽取式才有「页码+原文引用」。若赛题强调「引用可回溯」，需确认 LLM 回答也要挂 evidence。
